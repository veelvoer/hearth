# 1. Versions, release notes and the "what's new" popup

How Hearth does it:
- One number everywhere: `MAJOR.MINOR.PATCH`. `scripts/set-version.js` takes `feature` (new thing: minor+1, patch=0), `fix` (only bugs: patch+1), `major`, or an exact number, and writes it into desktop `package.json`, the relay `version.js` and the Android `versionName`, with `versionCode = major*10000 + minor*100 + patch`. It also creates `release-notes/X.Y.Z.md` as a stub with the word TODO in it.
- `release-notes/X.Y.Z.md` is the patch note of that version, written for normal users in plain words (no maintainer-only things, no secrets). A CI workflow (`.github/workflows/release.yml`, runs on a `vX.Y.Z` tag) refuses to release when the tag does not equal the version in all three places, when the notes file is missing, or when it still says TODO. The same file becomes the body of the GitHub release.
- The notes travel INSIDE the apps: Android `assets.srcDir("../release-notes")` in `build.gradle.kts`, Electron `extraResources` `{ from: "../release-notes", to: "release-notes" }`. After an update the app shows a popup "Updated to X" with the notes of every version since the last one the user saw (Hearth: `Updates.whatsNew()` in `Updates.kt`, last-seen version stored locally, nothing shown on a fresh install). Strip the markdown to plain bullets for the popup.
- Update check: ask GitHub `releases/latest` (first the cheap redirect of `https://github.com/<owner>/<repo>/releases/latest`, API as fallback so the rate limit never blocks it), compare numbers part by part, show "Update" in Settings → Updates. Phone downloads the APK and installs it through `PackageInstaller` (needs the "install unknown apps" permission, send the user to that setting when missing). Desktop downloads the installer. Keep Lodica's SHA-256 check and its existing flow where it is already good.
- Lodica's CHANGELOG.md / PATCH_NOTES.md can stay for history; new versions get a `release-notes/` file. Do the next release with the new scheme: this work is a `feature`.

# 2. The support system

How Hearth does it (read `support/app.js`, `support/server.js`, `support/mail.js`, `support/install.sh`, `support/test/support.test.js`, the screens `desktop/renderer/support.js` and `app/.../Support.kt`):
- A small separate Node service (own systemd unit, `NoNewPrivileges`, only listens on 127.0.0.1, behind the reverse proxy) with a mailbox (Gmail with an app password) for sending (nodemailer) and receiving (imapflow).
- Nobody makes an account: the app asks for an email address, the service mails a 6-digit code, the code gives a session token (stored hashed with sha256, 90 days). Rate limits everywhere (codes per address and per IP, requests per day, messages per day), bad domains refused through an MX lookup.
- A person writes a request (category bug / question / idea / other, title, text, optionally app + version + platform) and gets a number like HRT-48213 and a confirmation mail. They can list their requests and open a thread inside the app and answer there.
- The owner is mailed every new request and follow-up with `Reply-To` set to a plus-address (`support+HRT-48213@gmail.com`). When the owner replies to that mail, the service reads the mailbox by UID (never "unread", so reading it in Gmail cannot make it miss one), finds the ticket by the plus-address, removes quoted text, checks that the sender is an owner address AND that Gmail's `Authentication-Results` passed (otherwise anybody could fake an owner), adds the answer to the ticket and mails it to the person from the support address. Mails the service sends itself carry an `X-Hearth-Mail` header so it never answers itself. Failed sends go to an outbox that is retried every minute. All user text is HTML-escaped in every mail.
- Owners (the `SUPPORT_OWNERS` list) who sign in to the in-app support screen see EVERY request, read only (each request shows the sender address; writing into someone else's request is refused with 403, answers go by email so nothing is sent by accident).
- Owner notifications: when a request or follow-up arrives, the support service tells the owner's own server (`POST /support/incoming`, authenticated with the server's key, timing-safe compare) and the apps show a notification with three buttons: Give to Claude (starts a chat with the request in it), Add to list (saved in a list and optionally created as a Google Tasks task through OAuth with the single scope `tasks`), Ignore. Doing "Add to list" or marking it fixed makes the support service mail the person automatically ("added to our list", later "it is done" with a one-line note), once each, through `POST /owner/notify`. This owner part is optional: build the person-facing support system first, and the owner side only if I ask.
- Replace or extend Lodica's current support chat with this model only where it is clearly better; if I prefer to keep the chat UI, keep it and add the email flow behind it. Ask me which when in doubt. Do not break existing tickets.
- Setup things only I can do: the Gmail mailbox + app password, `SUPPORT_USER`, `SUPPORT_PASS`, `SUPPORT_OWNERS`, the systemd unit, the proxy route. Write an `install.sh` like Hearth's and tell me exactly what to run. NEVER put a password, token or key in the repository or in a log.
- Write tests for the service with a fake mail transport (Hearth's `support.test.js` is the model): sign-in code, wrong code, rate limits, escaping, owner reply goes out from the support address, fake owner (no auth pass) is refused, outbox retry.

# 3. System colors (follow the phone / the desktop)

How Hearth does it (`app/.../Theme.kt`, Settings → Appearance; `desktop/main.js` around `accentColor` and `desktop/renderer/app.js` `applyPalette`):
- Android: a setting "Colors: Hearth / System colors". With System colors on and Android 12+ (SDK 31), use `dynamicLightColorScheme(context)` / `dynamicDarkColorScheme(context)` (Material You, taken from the wallpaper) for the whole app; otherwise the app's own palette. Light/dark always follows the phone. Hide or explain the option on older Android. For GeckoView pages keep web content's own colors; only the app chrome follows (and make the Lodica start page and in-app pages use the same accent through CSS variables).
- Desktop: palette choices = default, a few swatches, a custom color, and "My desktop". "My desktop" uses the operating system's accent color: Windows and macOS through `systemPreferences.getAccentColor()`; on Linux every desktop differs, so ask in this order and take the first answer (Hearth's `systemAccent()` in `desktop/main.js` has all of it): 1) the xdg-desktop-portal `org.freedesktop.appearance` `accent-color` (a triple of floats, via `gdbus call --session --dest org.freedesktop.portal.Desktop ... org.freedesktop.portal.Settings.Read`), 2) KDE Plasma `~/.config/kdeglobals` line `AccentColor=r,g,b`, 3) Hyprland's focused border color (`hyprctl getoption general:col.active_border -j`), 4) GNOME's `gsettings get org.gnome.desktop.interface accent-color` (a name like `blue`: map it to a hex; ONLY on GNOME-like desktops, elsewhere it always says blue), 5) the GTK theme's `@define-color accent_bg_color` in `~/.config/gtk-4.0/gtk.css` or `gtk-3.0/colors.css`, then the default. Cache the answer for ~15 s and poll, so a change of the OS accent shows up without a restart. Extend Lodica's existing `systheme.js` (it already finds dark/light on Linux) with this instead of making a second file.
- The renderer sets CSS variables from the chosen accent (main color, hover, soft tints with `color-mix(in srgb, var(--accent) 12%, transparent)`, text color that stays readable on the accent: pick black or white by luminance). Everything that used a hard-coded brand color must use the variable. Check light AND dark, and that contrast is readable.
